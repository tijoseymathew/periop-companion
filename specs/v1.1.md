# PeriOp Companion — Eval Harness v1.1: NAT-native evaluators

**Moves the provenance/claim/extraction eval harness from a standalone script onto `nat eval`, closing the gap between what [specs/v1.md](v1.md) §6 describes and what the codebase actually runs.**

Version: 0.1 (draft for review)
Status: Companion to [specs/v1.md](v1.md). Addendum to §6 (Evaluation) — supersedes `scripts/run_eval.py` as the eval harness entry point once implemented; does not change §3–5 (architecture, Case object, synthetic data pipeline) or the metric definitions themselves.

---

## 1. Gap this closes

v1 §3.1's design rule is "ADK owns orchestration, NAT owns observability and evaluation," and §6 says metrics are "custom NAT evaluators" run via `nat eval`. In practice:

- `configs/eval_config.yml` documents an intended `_type` mapping for 7 evaluators, but none are registered — `nat eval --config_file configs/eval_config.yml` fails today with unknown evaluator types.
- The only working `nat eval` config is `configs/profile_config.yml`, and it's used solely to collect NAT profiler traces (M5 README screenshot), not to score anything.
- Real scoring happens in `scripts/run_eval.py`, a standalone script that loops over `data/cases/*`, re-runs the pipeline if a case isn't cached, loads gold via `synthgen.bundle.load_gold`, calls `evals.harness.evaluate_case`, and writes `evals/report.json` — entirely outside NAT's evaluator plugin system.

This addendum registers the existing metrics (`src/periop/evals/metrics.py`) as real NAT evaluators, retires the standalone runner, and makes `nat eval` the one eval harness entry point (metrics, provenance report, and profiling all through the same CLI surface).

## 2. Design

### 2.1 Evaluators wrap, not reimplement

Each NAT evaluator is a thin `BaseEvaluator` subclass over the metric functions that already exist. No metric logic is duplicated — this is what keeps the NAT path and today's numbers (`evals/report.json`, `evals/README.md`) in sync by construction rather than by discipline.

Per `evaluate_item(item: EvalInputItem)`:
1. Load the processed `Case` from `CaseStore(case_dir / "_out").load(item.id)`.
2. Load the `GoldCase` from `synthgen.bundle.load_gold(case_dir / item.id)`.
3. Call the corresponding function in `periop.evals.metrics` and return an `EvalOutputItem(score=..., reasoning={...})`.

Evaluators intentionally ignore `item.output_obj`/`expected_output_obj` (the NAT dataset's generic answer-scoring channel) — a `Case` is a claims graph, not a scalar string, and it's already fully reconstructable from `item.id` plus files on disk. This is a deliberate deviation from NAT's typical "score the generated answer against the expected answer" shape; call this out in the config comments so it doesn't read as an oversight later.

### 2.2 Evaluator inventory

One config type per row; two rows share a type via an `artifact` field. This matches exactly what `evals.harness.CaseReport` already tracks — no new metrics invented, no asymmetries smoothed over (e.g. `provenance_precision` and `hallucinated_claim_rate` remain single-artifact, matching current harness behavior).

| `_type` | config fields | yaml keys (instances) | needs judge? |
|---|---|---|---|
| `periop_provenance_coverage` | `case_dir`, `artifact: preop_note\|handoff` | `preop_provenance_coverage`, `handoff_provenance_coverage` | no |
| `periop_provenance_precision` | `case_dir` | `preop_provenance_precision` | no |
| `periop_claim_recall` | `case_dir`, `artifact: preop_note\|handoff` | `preop_claim_recall`, `handoff_claim_recall` | yes (`LlmJudge.matches`) |
| `periop_gap_analysis_prf` | `case_dir` | `gap_analysis_prf` (score=f1, reasoning carries p/r) | yes (`LlmJudge.question_matches`) |
| `periop_distractor_leakage` | `case_dir` | `distractor_leakage` | yes (`LlmJudge.matches`) |
| `periop_hallucinated_claim_rate` | `case_dir`, `artifact: handoff` | `handoff_hallucination_rate` | no |
| `periop_extraction_f1` | `case_dir` | `extraction_f1` (score=f1, reasoning carries p/r) | no |

9 yaml instances, 7 registered `_type`s.

Judge-based evaluators each construct their own `LlmJudge(chat=fast_chat())` — one per evaluator instance, not shared across evaluators. `LlmJudge` caches verdicts per `(kind, pred, gold)` pair internally, so this only duplicates judge calls *across* evaluator types scoring the same pair (e.g. `preop_claim_recall` and `handoff_claim_recall` never compare the same pairs, so no waste there); a shared cross-evaluator cache is a possible future optimization, not required for this pass.

### 2.3 Dataset

New file `data/cases/_index.json`: one row per complete case (has `gold/gold.json`):

```json
[{"id": "sg-0001", "question": "sg-0001"}, {"id": "sg-0002", "question": "sg-0002"}, ...]
```

`question` (the structured input key `nat eval` feeds to the workflow) holds the case_id string — exactly what `periop_pipeline`'s function already takes as input. `answer` is left unused; gold is loaded from disk by the evaluators as described above, not from the dataset row.

### 2.4 Registration wiring

New module `src/periop/nat/evaluators.py` holds the 7 `@register_evaluator`-decorated config/builder pairs. `src/periop/nat/register.py` imports it (`from . import evaluators`) so the existing single `nat.components` entry point (`periop = "periop.nat.register"`) picks up the registrations — no `pyproject.toml` change, keeping the narrow ADK/NAT seam from §3.1/§10 intact.

### 2.5 Config

`configs/eval_config.yml` changes:
- `eval.general.dataset.file_path` → `data/cases/_index.json`
- `eval.general.output_dir` → `evals/nat/` (mirrors `profile_config.yml`'s pattern)
- `eval.evaluators` → the 9 concrete entries from §2.2, replacing the current 7 placeholder entries

`nat eval --config_file configs/eval_config.yml` then runs the pipeline over every case in the dataset (via `periop_pipeline`, which already checks `CaseStore` before re-running — so cases with cached `_out` entries score without re-generation, same resumability `scripts/run_eval.py --rerun` opted out of by default) and scores each with all 9 evaluators, writing NAT's own aggregate + per-item output under `evals/nat/`.

## 3. Retiring `scripts/run_eval.py`

Once the evaluators land, `scripts/run_eval.py`'s orchestration (loop over cases → run pipeline if needed → load gold → score → aggregate → write JSON) is fully subsumed by `nat eval` over `configs/eval_config.yml`. Decision: **retire it**, not keep it alongside.

- Delete `scripts/run_eval.py`.
- `evals/report.json` / `evals/README.md` generation moves to `nat eval`'s own output (`evals/nat/`); update any README / `docs/progress.md` references accordingly.
- The `--only <case_ids>` dev convenience `scripts/run_eval.py` had maps to `nat eval`'s dataset filtering (`eval.general.dataset.filter`, or a scratch dataset file listing a subset) — document the equivalent invocation in README rather than keeping a second code path.

---

## 4. Testing

New `tests/test_nat_evaluators.py`, following `tests/test_nat_workflow.py`'s pattern:
- Build a tmp `case_dir` with a stub `Case` (pre-saved via `CaseStore`) and a matching gold bundle.
- Monkeypatch `periop.evals.judge.LlmJudge` (or its `chat`) for the judge-based evaluators so tests stay deterministic and offline, same as existing tests monkeypatch `nim.reasoning_chat`/`nim.fast_chat`.
- Construct an `EvalInput` directly and call each registered evaluator's `evaluate_fn`, asserting scores against hand-computed expectations (same fixtures `tests/test_evals_*` already use for the underlying metric functions, so behavior is cross-checked rather than re-derived).

---

## 5. Non-goals

- No new metrics beyond what `evals.harness.CaseReport` already computes.
- No change to the Case object, provenance model, or synthetic data pipeline (v1 §3–5 stand as-is).
- No cross-evaluator judge-cache sharing (noted as a possible follow-up in §2.2, not required here).
- `configs/profile_config.yml`'s profiling role is unchanged; it stays a separate, smaller config for the profiler-only run referenced in the README.
